# 小红书、地图降级与天气并行规划架构

## 目标与路由边界

会话保存的规划来源决定入口语义：

| `planning_source` | 入口 | 内容事实来源 |
| --- | --- | --- |
| `standard` | 默认值或登录卡片“跳过” | 高德 POI、距离矩阵、路线与天气 |
| `xhs` | 用户显式开启“小红书原帖” | 小红书笔记详情正文，不查天气 |

`standard` 模式下，普通聊天和单项工具查询仍进入 `AgentExecutor`。`xhs` 是显式原帖检索模式，
因此当前消息无论是否为多日行程表达，都会直接用于 MCP 搜索，不进入 LLM 路由。

## 请求契约

标准地图规划的 `CityTripRequest` 承载：

- 必填：`destination_city`、`duration_days`、`start_date`。
- 可选：`interests`、`food_preferences`。
- 第 N 天日期固定为 `start_date + N - 1`，首尾日期均包含。
- 用户最近一轮显式城市、天数或日期覆盖模型提取结果。
- 支持 ISO 日期、中文年月日、无年份月日以及今天/明天/后天；相对日期按
  `Asia/Shanghai` 请求上下文解析。

这些校验只属于 `standard` 地图规划。`xhs` 模式不提取或校验城市、天数、开始日期，最新一条用户
消息经空白规范化和 200 字符限制后直接成为搜索词。

## 执行与取消

```text
planning_source=xhs
└─ 检查登录 → 搜索/详情 → 确定性渲染原帖 → SSE（无 LLM、无天气）

planning_source=standard
└─ LLM 路由 → 提取并校验城市/天数/日期
   ├─ 缺字段/无效值 → 合并追问，结束
   └─ 并行收集地图地点/路线与天气
      → 结构化生成 → 服务端校验 → 渲染/SSE
```

并发由服务层显式创建任务，不交给模型决定。父请求取消会向全部子任务传播；取消登录等待时，后端
还会调用 MCP 的登录取消能力。登录卡片的跳过操作会中止旧 SSE，并立即在同一会话创建一个
`planning_source="standard"` 的新请求。前端只保留一个活动流，并用请求内集合阻止同一卡片重复
点击产生多个地图规划。

天气不会在登录等待期间预取，避免用户长时间不操作或改选地图模式时浪费配额、使用过期预报。

## 天气证据

`WeatherEvidenceService` 每次规划最多执行一次逻辑天气查询，固定请求目标城市的高德预报。服务按
供应商返回的具体日期映射到每个自然日，不按数组位置猜测：

- 匹配成功：记录日/夜天气、温度、风向和风力。
- 部分或全部超出预报范围：对应日期为 `unavailable`，行程继续生成并显示原因。
- 调用失败：全部日期为 `unavailable`，只暴露安全摘要，不泄露 Key、URL 或内部异常。

`TripWeatherEvidence` 保留 provider、城市、adcode、查询时间、供应商报告时间、逐日覆盖和警告。
它直接进入本次规划运行态和生成输入，不在生成阶段反向读取缓存。底层 `AmapClient` 仍可命中已有
5 分钟进程内缓存；本次没有新增 Redis 或数据库天气表。

## 小红书模式

登录完成后只收集小红书正文，不启动天气或生成模型：

- 查询取最新用户消息，使用 `most_liked` 与其余 `any` 筛选。
- 首次结果中按标准化点赞量选详情候选，最多取得两篇有效正文。
- 正文不按模型输入预算截断，服务端只添加来源元数据，不摘要或改写。

`xsec_token` 只存在于 MCP 适配边界，不进入模型提示、规划状态、普通日志或数据库。

## 地图证据收集与优化

地图模式使用确定性算法先固定地点和顺序，再把证据交给模型润色。

### 景点

1. 搜索目标城市景点，并可根据兴趣补充最多两个查询。
2. 丢弃缺少 POI ID/GCJ-02 坐标、跨城市、明显非景点或重复候选，最多保留 20 个。
3. 计算景点步行时间矩阵，以贪心最短衔接把景点两两分日；每天最多两个，第二个固定为下午景点。
4. 证据不足时减少景点并写入警告，不使用低质量或跨城市 POI 凑数。

### 三餐与五点顺序

每天固定为：

```text
早餐 → 上午景点 → 午餐 → 下午景点 → 晚餐
```

早餐、午餐、晚餐分别围绕相邻景点搜索，默认半径为 1500、2500、1500 米；无结果时扩大条件重试
一次。候选同样必须具备有效 POI ID、坐标并通过城市校验。每日最多将 17 个位置放入距离矩阵，枚举
最多 125 个三餐组合，以四段总步行距离、耗时、超阈值惩罚和全程餐厅去重选择稳定解。缺少某餐
时保留固定位置的占位警告，不让模型补造餐厅。

### 路线

相邻两点的步行距离不超过 1500 米且耗时不超过 20 分钟时，使用距离矩阵事实。任一指标超限时只
对最终入选路段查询高德公交路线。公交失败时，路线标记为 `unverified`，保留已知步行事实并提示
出发前导航确认，不编造公交线路、距离或耗时。

地点证据保留引用 ID、角色、POI ID、名称、地址、类型、GCJ-02 坐标、搜索词和查询排名；路线
证据保留起终点引用、方式、距离、耗时与供应商摘要。

## 标准地图模式的结构化生成与服务端校验

模型只生成推荐理由、体验方向、天气建议和自然语言提示。地点引用、五点顺序、日期、天气与路线
端点必须与证据包严格一致。服务端校验：

- 天数、连续 `day_index` 和日期范围；
- 每日地点引用集合与固定角色顺序；
- 路线起终点是否等于相邻地点；
- 天气日期是否等于当日日期；
- 是否出现证据集以外的具体地点引用。

首次输出不合法时只允许一次受控修订；仍不合法则返回安全错误，不渲染未经验证的攻略。最终
Markdown 由服务端固定渲染地点元数据、路线事实、天气事实、provider、查询时间、报告时间和警告，
避免模型覆盖证据字段。

## API、SSE 与持久化兼容

- `ChatRequest.planning_source` 默认为 `standard`，只接受 `standard` 或 `xhs`。
- `Conversation.planning_source` 持久化会话级选择，新对话默认关闭小红书，历史对话重新打开后恢复。
- 现有 `xhs_login_required` 事件未改名，只新增默认可省略的 `fallback_available` 和
  `fallback_mode`。
- 旧前端忽略新增 SSE 字段后仍可继续显示原登录卡片。
- 数据库只新增规划来源枚举值，不保存登录 ID、MCP Token 或完整工具原始响应。

## 已知运行边界

- 天气可用范围受高德预报窗口限制，超范围日期只能明确标记不可用。
- 缓存为单进程、5 分钟 TTL，服务重启或多进程之间不共享。
- 餐厅评分、营业状态、排队、招牌菜，景点票价、开放时间和预约政策均不在当前事实范围内。
- 地图优化是有界确定性启发式算法，不是复杂的全局旅行商求解器。
