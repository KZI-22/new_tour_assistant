# 小红书原帖检索链路

## 路由边界

`planning_source=xhs` 表示用户显式选择“原帖检索模式”。`ChatService` 在创建业务模型和调用
`TripRequestRouter` 之前直接进入 `XhsTripPlanner`，因此该链路不使用 LLM，也不执行城市、天数、
日期提取、天气查询或行程生成。`planning_source=standard` 的地图行程和普通 Agent 行为保持不变。

## 执行流程

```text
取最新一条用户消息，合并空白并限制为 200 字符
→ 检查小红书登录状态
→ 未登录时 MCP 打开本机 Chrome，等待人工验证
→ 使用原消息作为 keyword，以 most_liked 搜索首次加载结果
→ 过滤、去重并按点赞量读取最多五篇可用详情候选
→ 选择最多两篇有效正文
→ 服务端确定性渲染标题、作者、时间、点赞量、笔记 ID 和正文
→ 通过 SSE 返回
```

搜索词完全由程序生成，不由模型扩写。正文采用 MCP `NoteDetail.description`，仅移除首尾空白，
不按提示词预算截断、不摘要、不改写。Markdown 包装只添加来源元数据和使用说明，不修改正文内容。

## 登录与错误恢复

登录会话 ID 只存在于当前 SSE 运行态。连接取消时，后端会取消轮询并请求 MCP 终止登录会话。
如果搜索时发现登录失效，链路会重新检查登录、完成人工验证并重试一次搜索。Chrome 登录状态由 MCP
独立保存在 `%LOCALAPPDATA%\xhs-read-mcp\chrome-storage_state.json`，主 API 不读取该文件。

## 数据与安全边界

- `xsec_token` 只用于同一条搜索结果的详情调用，不进入状态、Trace、最终回复或普通日志。
- 搜索只覆盖首次加载结果，不滚动、不分页，也不声称覆盖平台全部内容。
- 默认正文至少 200 字，最多返回两篇；候选详情读取失败时跳过并给出说明。
- 最终渲染回复会作为普通助手消息保存到会话；MCP 原始响应不会另行写入数据库。
- 原帖属于作者主观体验，时间、价格、营业状态和预约规则仍需用户复核。

## 传输

业务层通过同一个 `XhsMcpClient` 兼容 `stdio` 与 `streamable-http`。`stdio` 在首次工具调用时懒启动
本机 MCP 子进程并在 FastAPI 关闭时回收；HTTP 模式连接已经独立运行的 MCP 服务。传输差异不会
改变原帖选择与输出语义。
