# 小红书旅游攻略规划链路

## 路由边界

`ChatService` 只保留两条顶层路径：普通聊天与单项旅游查询进入 `AgentExecutor`，创建或调整城市
多日攻略进入 `XhsTripPlanner`。规划链路不会查询或编排实时机票、火车票、酒店库存和价格；混合
请求中的这类附带查询会在最终说明中明确标记为未执行。

## 执行流程

```text
提取目标城市和游玩天数
→ 缺少字段时追问并结束本轮
→ 检查小红书登录状态
→ 未登录时返回二维码并轮询扫码状态
→ 使用固定关键词和 most_liked 筛选搜索首次加载结果
→ 过滤、去重并按标准化点赞量选择最多五篇详情候选
→ 每批最多并发读取两篇，取得两篇有效正文后停止
→ source_1 / primary 决定主体路线
→ source_2 / supplementary 只补充主帖缺少的信息
→ 单次结构化模型调用生成指定天数的攻略
→ 校验天数与活动来源，服务端重建来源元数据
→ 渲染 Markdown 并通过 SSE 返回
```

登录二维码只存在于当前 SSE 和浏览器内存状态，不进入助手正文或 PostgreSQL。连接取消时会取消
本地轮询并请求 MCP 终止当前登录会话。

## 搜索与证据边界

搜索词严格为 `{城市} {天数}日游 攻略`，筛选固定为
`most_liked/any/any/any/any`。系统只使用搜索页首次加载结果，不滚动、不分页，也不声称覆盖平台
全部内容。点赞量支持普通数字、千和万等常见中文格式；无法解析时保留 MCP 原顺序。

详情候选必须同时包含同一搜索条目的 `note_id` 和 `xsec_token`，正文长度默认至少 200 字。
`xsec_token`、MCP Bearer Token、二维码、Cookie 和完整正文不得写入普通日志或数据库。

## 生成与来源约束

主帖决定总体路线、每日结构、主要地点和核心建议；辅帖只补充餐饮、提醒、替代玩法或明显不足的
某一天。发生冲突时主帖优先。每个具体活动必须引用本次实际读取的 `source_1` 或 `source_2`，
引用为空或越界会直接结束本轮，不追加模型修复调用。最终来源的角色、作者和点赞量由服务端根据
研究结果重建，不接受模型自行提供的来源元数据。

## 持久化兼容

当前链路只持久化会话和最终助手消息，不再写入旧结构化 Planner 的 `travel_plans` 与
`travel_plan_versions`。历史 ORM 模型、数据库表、数据和 Alembic 迁移继续保留；本次切换不执行
破坏性数据迁移。
