## 二、问题摘要与已确认事实

### 1. 两天需求被扩展成三天

用户明确输入：

```text
从南京出发，后天出发，玩2天
```

以 `Asia/Shanghai` 时区和 2026-07-18 为当前日期，正确的规范化结果应为：

```json
{
  "start_date": "2026-07-20",
  "end_date": "2026-07-21",
  "duration_days": 2
}
```

数据库实际保存为：

```json
{
  "start_date": "2026-07-20",
  "end_date": "2026-07-22",
  "duration_days": 3
}
```

错误的结束日期继续影响了返程查询、酒店退房、天气覆盖、每日行程、餐饮预算和最终标题。

### 2. 交通供应商返回了数据，但本地归一化为零条

事故会话中的 4 次交通调用全部被记录为成功，但收集阶段得到：

```text
4/4 个工具调用成功，标准化得到 0 条可用记录，覆盖 0/2 个必要查询方向。
```

使用相同参数复查真实响应时：

| 工具 | 供应商候选数 | 当前归一化结果数 |
|---|---:|---:|
| 南京到西安航班 | 10 | 0 |
| 南京到西安火车 | 10 | 0 |

FlyAI 当前响应使用 `itemList -> journeys -> segments` 层级，关键字段包括：

- `marketingTransportNo`
- `depCityName` / `arrCityName`
- `depDateTime` / `arrDateTime`
- `depStationName` / `arrStationName`
- `seatClassName`
- 外层 `ticketPrice` 或 `price`
- 以分钟表示的 `duration` / `totalDuration`

现有通用映射既不完整识别这些字段，也不能把外层价格与内层班次关联起来。

### 3. 工具“调用成功”和“产生可用业务数据”没有区分

当前 `tool_result.success=true` 只代表工具进程或供应商响应成功。即使后续归一化为零条，工具卡片仍可能显示成功，造成“工具显示成功但最终没有结果”的矛盾体验。

数据库审计只保存参数、通用摘要、错误码和耗时，没有保存安全的候选数、归一化数、响应 schema 版本或数据质量状态。事故复盘必须重新请求供应商才能确定原因。

### 4. 展示给用户的未完成方案没有被结构化保存

事故会话中的 `travel_plans` 记录为：

```text
status=draft
current_version=0
plan_json=null
```

最终 Markdown 虽然展示了一个三日草案，但数据库只保留需求，没有保留该草案。用户后续要求“修改第二天”时，系统没有可继续编辑的结构化方案。

### 5. POI 与酒店路线质量不足

默认宽泛关键词召回了“山西地标产品展销中心”“地标市集”等低相关结果。当前排序更重视坐标密度与供应商顺序，缺少目的地城市一致性、查询意图、POI 类型和旅行价值校验。

FlyAI 酒店结果可以包含名称和地址，但没有可靠坐标时，系统不会继续做受控的高德精确匹配，导致酒店无法纳入路线验证。

## 三、修复目标

本次修复完成后必须达到以下结果：

1. 用户明确表达的日期、天数和晚数是硬约束，不能被 LLM 推断静默覆盖。
2. 日期字段只有一个明确、可测试的语义：`start_date` 和 `end_date` 均为行程包含的自然日，`duration_days = end_date - start_date + 1`。
3. FlyAI 航班和火车真实响应可以稳定转换为 `TransportOption`，价格、时间、车次/航班号和耗时单位正确。
4. 供应商调用状态、标准化状态和业务可用状态分开表达。
5. 未通过正式校验的 partial plan 仍可安全保存和继续修改，但不能冒充正式版本。
6. POI 不足时宁可减少活动并给出提示，也不能使用明显低相关地点凑满行程。
7. 原有普通聊天、单项工具查询、停止生成、历史对话、数据库旧数据和 SSE 客户端保持兼容。

## 四、非目标

本次修复不包含：

- 更换 FastAPI、LangGraph、PostgreSQL、Next.js 或现有模型供应商。
- 接入新的航班、酒店或地图供应商。
- 自动预订、支付或声称库存已锁定。
- 重写整个 Agent 架构。
- 为了解决本次问题而同时引入用户账户、权限系统或新的前端状态框架。

## 五、必须保持的系统不变量

任何阶段违反下列条件都不得合并：

### 1. 事实边界

- 工具没有返回的班次、价格、酒店、POI ID、坐标和天气不得由模型补造。
- 经验估算必须标为估算，不能与实时工具价格混为一类。
- 原始供应商数据是不可信输入，不能直接拼入系统指令或作为 HTML 渲染。

### 2. 日期边界

- 相对日期始终基于请求上下文中的当前时间和 `Asia/Shanghai` 时区。
- 明确用户原文的优先级高于模型推断。
- 同一字段的优先级为：本轮明确用户表达 > 以前轮次明确表达 > 已保存请求 > LLM 补全。
- 日期和天数发生冲突时必须确定性纠正或向用户澄清，禁止静默选择冲突值。

### 3. 协议兼容

- 现有 SSE 事件名不得直接删除或改名。
- 新增 SSE 字段必须可选，旧前端忽略后仍可工作。
- 已有数据库记录必须继续可读。
- 数据库迁移只允许先增加可空字段或新表，不在同一发布中删除旧列。

### 4. 持久化边界

- 正式方案与 partial/draft 方案必须在状态上可区分。
- 校验失败的修订不能覆盖最后一个正式版本。
- 保存失败不能影响对话消息的最终状态更新，也不能留下半写入版本。

### 5. 工作区保护

- 当前仓库已有未提交改动，实施前必须先记录 `git status` 和相关文件 diff。
- 不得使用 `git reset --hard`、覆盖式 checkout 或删除用户已有改动。
- 每个阶段只修改计划列出的文件；发现范围外问题时单独记录，不顺手混入。

## 六、实施策略与质量闸门

修复分为六个阶段。每个阶段采用相同流程：

1. 先增加能够稳定复现缺陷的失败测试。
2. 只实现该阶段的最小生产代码变更。
3. 运行该阶段定向测试。
4. 运行全部非实时后端测试。
5. 运行 Ruff、前端类型检查、前端 Lint 和生产构建。
6. 检查数据库/SSE/JSON 兼容性和 `git diff --check`。
7. 阶段验收通过后才能进入下一阶段。

禁止把多个 P0 修复压在一个不可拆分的大提交中。建议一个阶段一个提交；数据库迁移与使用迁移的业务代码至少分成可审阅的独立提交。

## 八、阶段 1（P0）：修复日期与天数约束

### 设计

把“模型抽取”和“规范化请求”拆成两个概念：

```text
用户原文 + 已保存请求
        ↓
LLM 候选字段（允许不完整，但不能直接成为事实）
        ↓
确定性约束提取与字段来源标记
        ↓
冲突协调
        ↓
内部一致的 TripRequest
```

建议增加内部候选结构或协调函数，避免 `TripRequest` 在不知道字段来源的情况下静默覆盖值。持久化 JSON 结构保持不变，优先不做数据库迁移。

### 协调规则

- 只给出 `start_date + duration_days`：计算 `end_date = start_date + duration_days - 1`。
- 只给出 `start_date + end_date`：计算包含首尾的 `duration_days`。
- 三者齐全且一致：直接接受。
- 三者齐全但冲突：

  - 本轮用户明确说了天数时，以天数为准并重算 `end_date`。
  - 本轮用户明确给出日期区间时，以日期区间为准并重算天数。
  - 同一句话同时给出冲突的日期区间和天数时，停止查询并要求用户确认。
  - 只有 LLM 推断发生冲突时，舍弃冲突推断，使用可验证字段重新计算。

- “玩 2 天”表示 2 个行程自然日，不解释为 2 晚。
- “住 2 晚”表示退房日为入住日加 2 天，不自动等同于 2 日游。
- 修改已有方案时，本轮明确日期约束只覆盖相关日期字段，不能清空目的地、人数、兴趣等未修改字段。

### 生产代码改动方向

- 将用户原文明示的天数、日期区间和住宿晚数解析为带来源的确定性约束。
- 调整 `TripRequest` 日期 validator：

  - 可以补全缺失字段。
  - 不得静默覆盖一个已提供但冲突的字段。
  - 规范化后必须满足内部一致性。

- 在 `understand_request` 结束前完成协调，并在调用任何外部工具前检查一致性。
- 在生成、校验和渲染阶段增加同一日期不变量断言，形成纵深防御。

### 必测用例

| 用户输入 | 预期开始 | 预期结束 | 预期天数 |
|---|---|---|---:|
| 后天出发，玩2天 | 2026-07-20 | 2026-07-21 | 2 |
| 后天出发，玩两天 | 2026-07-20 | 2026-07-21 | 2 |
| 7月20日到22日 | 2026-07-20 | 2026-07-22 | 3 |
| 7月20日出发，住2晚 | 2026-07-20 | 待行程语义确认 | 不强行等于2 |
| LLM 返回 7月20日至22日，但用户说玩2天 | 2026-07-20 | 2026-07-21 | 2 |
| 用户同时说 7月20日至22日、只玩2天 | 追问确认 | 追问确认 | 不调用工具 |

还需覆盖月末、年末、闰年、过去日期、不同请求时区和已有草稿的后续补充。

### 退出标准

- 事故输入稳定得到 2 天且只生成两个 `DayPlan`。
- 交通返程日期和酒店退房日期使用 2026-07-21。
- 冲突输入不会触发航班、火车、酒店、天气或路线查询。
- 原有日期范围、修改行程和缺失字段测试全部通过。

## 九、阶段 2（P0）：实现 FlyAI 交通专用适配器

### 设计

不要继续依赖“递归遍历所有 mapping + 大量字段别名”的通用猜测方式。为 FlyAI 航班和火车响应建立显式、版本化的适配边界：

```text
FlyAI 原始 JSON
    ↓ 校验 envelope
itemList
    ↓ 逐 item
journeys
    ↓ 逐 journey
segments
    ↓ 首段/末段/全段聚合
TransportOption
```

### 字段映射

每个 journey 至少按以下规则聚合：

- 出发城市、车站和时间取第一段。
- 到达城市、车站和时间取最后一段。
- 航班号或车次来自所有 `marketingTransportNo`：

  - 直达保留单个号码。
  - 中转使用稳定、可读的组合引用，并在模型字段能力不足时保留到 `source_reference`，不得伪装成单一班次。

- 价格从所属外层 item 获取：航班优先 `ticketPrice`，火车优先 `price`。
- 总耗时优先 `totalDuration`，单位固定解释为分钟；单段 `duration` 同样按分钟处理。
- 舱位或席别来自 `seatClassName`。
- `queried_at`、provider、source tool 和稳定 source reference 必须保留。
- 无法解析价格时价格留空，但不能因此丢弃一个有班次号和时间的合法选项。
- 一条候选畸形时只跳过该候选并计数，不能让整批结果失败。

### 数据质量诊断

适配器输出除了选项外，还应提供安全统计：

```json
{
  "provider_item_count": 10,
  "journey_count": 10,
  "normalized_count": 9,
  "rejected_count": 1,
  "schema_version": "flyai-transport-v1"
}
```

如果 `provider_item_count > 0` 且 `normalized_count == 0`，返回明确的 `PROVIDER_SCHEMA_MISMATCH` 或等价数据质量诊断，不能只显示“查询完成”。

### 测试层次

- 单元测试：字段映射、分钟单位、价格继承、首末段聚合、去重和候选上限。
- 契约测试：使用阶段 0 的真实形状 fixture。
- 收集器测试：验证去程、返程两个方向均有覆盖。
- 图测试：验证班次可以进入生成 Prompt、验证器和最终渲染。
- 实时测试：保留 `flyai` marker，手工或 CI 凭据环境显式执行，不作为日常离线测试前提。

### 兼容与回滚

- 旧通用适配器在新适配器通过契约测试前不删除。
- 可以在开发环境对同一脱敏 fixture 同时运行新旧解析器并比较数量。
- 上线时优先使用一个可回退配置开关；新适配器发生异常时降级到旧逻辑并产生告警，禁止无声回退。

### 退出标准

- 事故 fixture 中航班和火车均至少产生一个完整 `TransportOption`。
- `duration="120"` 得到 120 分钟，而不是 7200 分钟。
- 外层价格正确关联到对应 journey。
- 去返程方向校验通过，首日和末日活动边界能够使用真实到达/出发时间。
- 畸形候选不会影响同批正常候选。

## 十、阶段 3（P1）：修复工具状态、审计和前端可见性

### 状态模型

必须区分三层状态：

| 层次 | 示例状态 | 含义 |
|---|---|---|
| 执行状态 | success / failed / timeout | 工具是否完成调用 |
| 数据状态 | usable / empty / invalid / partial | 返回是否能标准化 |
| 业务覆盖 | covered / missing | 是否覆盖去程、返程等必要任务 |

已有 `success` 字段暂时保留，新增字段采用可选、向后兼容方式。旧前端只读取原字段仍应正常工作。

### SSE 与前端

- 工具刚返回但尚未标准化时，文案使用“查询已返回，正在处理”，避免提前显示业务成功。
- 归一化结束后更新对应工具或规划阶段，显示候选数、可用数和失败原因。
- 工具卡片需要区分：

  - 调用失败。
  - 调用成功但没有候选。
  - 调用成功但响应结构不兼容。
  - 获得 N 条可用结果。

- 新字段必须在前端运行时校验后再使用，未知状态安全降级为通用文本。
- 会话重新加载后至少能恢复安全的工具审计摘要；不要求把完整原始供应商响应发送到浏览器。

### 数据库审计

优先保存结构化的安全指标，不保存完整原始响应。建议采用向后兼容的可空 JSON 指标字段或独立审计记录，内容包括：

- provider item count。
- normalized item count。
- rejected item count。
- data status。
- adapter/schema version。
- required direction 和是否覆盖。

如果需要 Alembic 迁移，采用 expand-first：

1. 先增加可空字段并验证旧代码仍可运行。
2. 再发布写入新字段的代码。
3. 最后让 API/前端读取新字段。
4. 本次不删除旧字段，也不要求历史记录回填为伪造数据。

### 退出标准

- “供应商成功、归一化为 0”不再显示为绿色的完整成功结果。
- 数据库能够仅凭安全审计指标区分供应商空结果和 schema mismatch。
- 旧 SSE 解析测试继续通过；新旧前端组合至少完成一次兼容测试。
- 工具原始响应、密钥和本地 CLI 路径不会出现在 SSE 或数据库审计中。

## 十一、阶段 4（P1）：保存并可继续修改 partial plan

### 设计

为首次生成但未通过正式校验的方案保存结构化 `plan_json`，状态仍为 `draft`，不能进入正式版本语义。

建议新增明确的服务方法，例如 `save_partial_plan`，而不是让现有 `save_draft` 同时承担“只有需求”和“已有未完成方案”两种含义。

### 行为规则

- 缺少必要信息、尚未生成方案时：保存 request-only draft，`plan_json=null`。
- 已生成但未通过校验时：保存 partial plan，`status=draft`，`plan_json` 非空，plan 内 `readiness=partial/blocked`。
- 首次正式通过校验时：创建 version 1，并设置 `status=active`。
- 已有 active plan 的修订失败时：保留原 active plan 和版本，失败候选不得覆盖正式方案。
- 加载 draft partial plan 后，用户可以修改第二天、交通方式或酒店，并只重查受影响区域。
- partial plan 解析失败时返回明确诊断，不把损坏 JSON 当作空计划继续运行。

### 并发与事务

- 继续使用行锁或等价并发控制，避免同一会话并发请求互相覆盖。
- request、plan、status、updated_at 必须在同一事务中提交。
- 消息完成状态与计划保存失败分别处理，避免一处失败留下错误的正式版本号。

### 必测用例

- request-only draft 后继续补充日期。
- 初次 partial plan 保存、重载和局部修改。
- active plan 修订失败后原版本不变。
- 同一会话两个并发保存请求。
- 旧 `plan_json=null` 草稿仍可读取。
- 损坏 plan JSON 返回受控错误。

### 退出标准

- 事故场景即使交通仍不可用，刷新会话后也能继续修改已展示的结构化草案。
- partial plan 不出现在正式版本历史中，除非后续通过校验。
- 原有版本递增、删除会话级联删除和数据库测试全部通过。

## 十二、阶段 5（P2）：提高 POI 和酒店路线质量

### POI 过滤与排序

- 保留并标准化供应商返回的城市、行政区、类型码、地址和查询来源。
- 有城市信息时要求与目标城市一致；跨城市候选默认拒绝或降为不可用。
- 根据查询意图对 POI 类型评分。例如“历史文化景点”应优先博物馆、历史遗址、古迹，不应优先特产销售中心。
- `must_visit` 精确命中优先于宽泛默认查询。
- 低相关商业地点、同名泛化地点和重复地点应降权或过滤。
- 设置最低相关性门槛。合格地点不足时生成更少活动并提示，不得为满足每日数量强行填充。
- 保留可解释的评分组成，测试只断言稳定规则，不断言供应商实时排序。

### 酒店坐标补全

- 仅对最终候选中的少量酒店做高德精确匹配，避免 N+1 查询。
- 查询使用酒店名称、地址和目标城市，并验证返回城市一致。
- 坐标来源、查询时间和匹配置信度必须保留。
- 匹配不确定时坐标保持为空，不把同名酒店坐标当作事实。
- 复用现有缓存和并发上限。

### 路线验证

- 酒店有可靠坐标后纳入每日首尾路线或代表性通勤校验。
- 路线矩阵截断前优先保留已选酒店、must-visit 和高相关 POI。
- 路线未覆盖全部必要路段时，`estimated_transport_time_minutes` 保持为空或标为部分覆盖，不能用经验值冒充已核验结果。

### 退出标准

- 固定 fixture 下“山西地标产品展销中心”不会进入西安历史文化行程。
- 合格 POI 不足时输出较少但可信的活动。
- 酒店坐标只有在城市与名称/地址匹配通过后才用于路线。
- 高德调用数量保持在配置上限内。

### 关键回归矩阵

| 场景 | 日期 | 工具 | 持久化 | 前端 |
|---|---|---|---|---|
| 普通问候 | 不解析行程 | 不调用 | 只存消息 | 正常流式文本 |
| 单项航班查询 | 使用明确日期 | AgentExecutor 调航班 | 工具日志可追溯 | 工具状态准确 |
| 两日完整规划 | 2 个自然日 | 去返程/酒店/POI/天气/路线 | ready 或 partial 可重载 | 只显示 2 天 |
| 缺少出发地 | 保存已知日期 | 不调用交通 | request-only draft | 只追问出发地 |
| 供应商空数据 | 日期不变 | data_status=empty | 保存 partial | 不显示伪成功 |
| 供应商 schema mismatch | 日期不变 | data_status=invalid | 保存诊断 | 显示结构不兼容 |
| 修改第二天 | 原日期不变 | 只重查活动/路线 | 新正式版本或保留旧版 | 显示变更摘要 |
| 修改为三天 | 明确变为 3 天 | 刷新所有时效数据 | 新版本 | 三个 DayPlan |
| 停止生成 | 不损坏请求 | 取消未完成调用 | 消息 interrupted | UI 可恢复 |
| 刷新历史会话 | 使用已存数据 | 不重复调用 | 加载消息、计划、审计 | 状态可恢复 |

### 事故场景最终验收

固定输入：

```text
帮我做一份去西安的旅游规划
从南京出发，后天出发，玩2天
```

固定当前时间：

```text
2026-07-18T10:39:13+08:00
```

必须同时满足：

1. `TripRequest` 为 2026-07-20 至 2026-07-21，共 2 天。
2. 只生成第 1 天和第 2 天。
3. 去程查询日期为 2026-07-20，返程查询日期为 2026-07-21。
4. 酒店入住为 2026-07-20，退房为 2026-07-21。
5. FlyAI 契约 fixture 的航班和火车均至少归一化一条。
6. 交通耗时单位和价格层级正确。
7. 工具卡片显示可用候选数，而不是只有通用“完成”。
8. 若任一必要方向缺失，方案标记 partial 且不虚构班次。
9. partial plan 刷新后可继续修改。
10. 低相关 POI 不用于凑数。

### 灰度策略

- 先在固定 fixture 和 Fake Model 环境完成全链路验证。
- 再在开发环境运行真实 FlyAI/Amap marker 测试。
- 如系统已有部署环境，先对少量内部测试会话开启新日期协调器和交通适配器。
- 观察至少以下指标：

  - 日期冲突数。
  - 供应商候选数与归一化数。
  - `PROVIDER_SCHEMA_MISMATCH` 数量。
  - 去返程覆盖率。
  - partial plan 比例。
  - 计划修改成功率。

- 指标异常时通过配置回退到上一个适配器；数据库新增字段保持可空，不需要破坏性回滚。
