# Trip Planner 规则优先提取改造计划

## 1. 已确认的方案

采用第二版方案：**代码规则优先，只有存在真实歧义时才调用 LLM，最后由代码统一组装和裁决**。

本次只改造进入 `trip_planner` 后的“提取行程与可选能力需求”阶段，不调整顶层路由、交通/酒店工具实现和后续行程生成链路。性能与准确率基线见仓库根目录的 [test.md](../../test.md)。

## 2. 改造目标

1. 对城市、天数、日期、交通、酒店等明确表达，使用代码在毫秒级完成解析。
2. 明确信息即使不完整，也不调用 LLM，直接进入缺失项校验和追问。
3. 只有指代、冲突或多种合理解释等真实歧义才调用 LLM。
4. LLM 只解析歧义字段，不再生成完整的 `TripPlanningRequest`。
5. 明确字段由代码拥有最终裁决权，LLM 不得覆盖用户已经明确表达的信息。
6. 保持现有 `ResolveCapabilitiesNode`、`ValidateRequirementsNode` 及下游链路的输入兼容。

## 3. 目标流程

```text
用户输入
  → 规则提取明确字段
  → 歧义检测
      ├─ 无歧义：直接组装 TripPlanningRequest
      └─ 有歧义：仅将歧义片段和候选值交给小型 LLM Schema
  → 按确定性优先级合并
  → 能力启用裁决
  → 缺失项校验与追问
  → 后续交通、酒店和行程规划节点
```

这里必须严格区分：

- **缺失**：用户没有提供出发地或出发日期。只有一种理解，不调用 LLM。
- **歧义**：存在指代不清、互相冲突或多个合理候选。只解析相关字段；无法消除时保留为空并追问，禁止猜测。

## 4. 设计要点

### 4.1 规则提取结果

新增一个内部提取结果模型，建议至少包含：

- `request`：已解析出的部分 `TripPlanningRequest`
- `field_sources`：各字段来源，如 `explicit_rule`、`conversation_context`、`llm_resolution`、`derived`
- `ambiguities`：待处理的歧义字段、原始片段和候选值
- `explicit_missing`：已确认缺失但不歧义的字段
- `capability_evidence`：交通、酒店开关的触发或否定证据

该模型只服务于提取流程，不要扩大对外 API Schema。

### 4.2 规则解析范围

第一阶段至少覆盖：

- 全局信息：目的地、行程天数、明确日期/日期范围、用户偏好
- 交通开关：查高铁、火车、飞机、交通票等正向表达，以及“不查交通”等否定表达
- 交通槽位：出发地、目的地、去程/返程日期、单程/往返、交通方式
- 酒店开关：酒店、住宿、住店等正向表达，以及明确否定表达
- 酒店槽位：入住/离店日期、预算、星级、行政区/商圈、地标或车站附近
- 常见天数表达：`三天`、`3天`、`三日游`、`3日游`
- 多轮上下文：继承仍有效的明确字段，用户本轮的明确更正优先

城市识别应复用现有城市/行政区数据或可靠的城市词典，不要只硬编码少量测试城市。

交通和酒店启用判断必须按分句或语义片段处理，不能用整段消息中是否出现一个否定词来覆盖所有能力。例如“不要飞机，查高铁和酒店”应得到 `need_transport=true`、`transport_mode=train`、`need_hotel=true`。

### 4.3 歧义检测

歧义检测应是独立、可单元测试的代码，重点识别：

- 多个并列候选且用户未做选择
- “那里”“附近”“那个车站”等无法唯一解析的指代
- 同一字段出现冲突值，且无法根据更正语气或最近明确表达裁决
- 交通或酒店条件的作用域存在多种合理解释
- 多轮信息与本轮信息冲突，但缺少明确的覆盖关系

字段缺失、没有日期、没有出发地本身不属于歧义。

### 4.4 LLM 歧义兜底

LLM 调用遵守以下约束：

- 只传入歧义所需的最小上下文、候选值和字段说明。
- 根据歧义类型使用小型 Pydantic Schema，不注入完整 `TripPlanningRequest` Schema。
- 输出使用精确 JSON，并通过 `StructuredOutputService` 或等价的统一结构化输出入口校验。
- 校验失败最多重试一次。
- 第二次仍失败或模型无法确定时，对应字段置空，交给缺失项追问；不得回退到完整 Schema LLM 提取。
- 没有歧义时不得产生 LLM 调用。

### 4.5 统一组装和裁决

建议使用以下优先级：

```text
本轮明确更正
  > 本轮其他明确规则值
  > 有效的历史明确值
  > LLM 对歧义字段的解析结果
  > 可安全推导的默认值
```

合并完成后，再由代码统一决定 `need_transport`、`need_hotel`，并调用现有能力解析和缺失项校验。日期、天数等明确值仍由代码覆盖，LLM 不能改写。

## 5. 预计改动位置

以实际代码结构为准，优先控制改动范围：

- 新增 `apps/api/app/services/rule_first_trip_requirement_extractor.py`
  - 规则提取
  - 歧义检测
  - 小型歧义解析调用
  - 确定性合并
- 修改 `apps/api/app/graphs/trip_planner_nodes.py`
  - 将 `ExtractRequirementsNode` 从“完整 Schema LLM 提取”切换为规则优先提取器
- 视需要修改现有日期/天数解析模块
  - 补齐 `X天`、`X日游`、日期范围等明确表达
- 视需要修改能力解析模块
  - 将交通、酒店的肯定/否定判断改为分句作用域
- 新增对应单元测试和端到端图测试

不要改动顶层路由的既有策略，也不要顺手重构交通、酒店供应商或生成节点。

## 6. 实施顺序

1. 固化测试集：保留当前 12 条开发用例，另增一组未参与规则开发的盲测用例。
2. 定义内部提取结果、字段来源和歧义描述模型。
3. 实现全局字段、交通和酒店的规则解析。
4. 实现分句级能力启用/否定裁决。
5. 实现歧义检测和按字段的小型 LLM Resolver。
6. 接入 `ExtractRequirementsNode`，保持后续节点协议不变。
7. 增加耗时、LLM 调用次数、触发原因和字段来源日志。
8. 跑单元、图集成和基准测试，再按独立修复创建 Git 提交。

## 7. 必测用例

核心验收样例：

```text
去西安三天旅游攻略，顺便查一下去西安的高铁，以及西安北站附近的酒店。
```

期望：

```json
{
  "destination_city": "西安",
  "duration_days": 3,
  "need_transport": true,
  "transport_mode": "train",
  "transport_scope": "round_trip",
  "transport_origin": null,
  "need_hotel": true,
  "hotel_nearby": "西安北站"
}
```

- 规则路径完成，LLM 调用次数为 0。
- 后续缺失项应包含出发地和出发日期。
- 不得因为字段缺失而调用 LLM。

还需覆盖：

- “去西安玩三天”：无交通、无酒店、0 次 LLM
- “去西安三日游，不查酒店”：酒店明确关闭
- “不要飞机，帮我查北京到西安的高铁和酒店”：交通与酒店均启用，交通方式为高铁
- 明确日期范围与相对日期
- 酒店地标/车站附近表达
- 本轮对历史城市、日期和天数的明确更正
- 多候选城市、指代不清、冲突日期等真实歧义
- LLM 首次非法 JSON、重试成功
- LLM 两次失败后字段为空并触发追问

## 8. 验收标准

- 明确样例的规则解析 P95 小于 50ms，不包含顶层路由和后续工具耗时。
- 无歧义请求的 LLM 调用率为 0。
- 有歧义请求只调用相关的小型 Resolver，每个解析请求最多重试一次。
- 上述核心样例结果完全正确。
- 盲测集能力路由准确率不低于 98%，核心字段和子模块槽位准确率不低于 95%。
- 代表性混合测试集的 LLM 触发率目标不高于 30%。
- 现有 trip planner 图、能力解析和结构化输出相关测试无回归。
- 日志能够区分 `rules` 与 `hybrid` 路径，并记录规则耗时、LLM 耗时、歧义字段和重试次数。

## 9. 风险与边界

- 城市别名和行政区覆盖不足会成为主要准确率风险，应使用可维护的数据源。
- 简单全局正则容易误判否定作用域，必须按分句裁决。
- 规则数量增长后应按领域拆分，避免形成不可维护的单文件正则集合。
- 盲测结果才用于最终准确率结论；当前 `test.md` 中的 100% 是开发集结果，不能直接视为生产准确率。
- 解析异常时应安全进入追问，不允许偷偷回退到原来的完整 `TripPlanningRequest` LLM 生成。
