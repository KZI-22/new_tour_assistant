# 小红书登录跳过、地图餐饮降级与天气并行执行计划

## 一、文档信息

- 状态：已实施，离线验收通过；真实高德验证未执行
- 编写日期：2026-07-20
- 实施记录：[`xhs_map_weather_fallback_execution_report.md`](xhs_map_weather_fallback_execution_report.md)
- 适用范围：城市多日攻略、小红书登录交互、地图景点与餐饮降级、天气并行查询、每日路线编排、前端过程展示
- 默认内容来源：小红书
- 降级内容来源：高德景点、餐饮、距离、路线与天气
- 实施原则：先补协议和失败测试，再逐阶段修改；任何阶段均不得伪造地点、天气、距离、营业时间或供应商事实

## 二、已确认的产品决策

本计划只落实以下已经确认的需求，不在实施中扩张范围：

1. 多日城市攻略默认进入小红书链路。
2. 用户未登录小红书时继续显示现有登录卡片，并增加“跳过登录，使用地图与天气生成”操作。
3. 用户点击跳过后，取消当前小红书登录等待，使用同一会话中的城市、天数和日期进入地图降级链路。
4. 地图降级链路不查询航班、火车、酒店、价格或库存。
5. 地图降级链路每天默认安排两个景点，第二个景点是下午景点。
6. 每日顺序固定为：

   ```text
   早餐 → 上午景点 → 午餐 → 下午景点 → 晚餐
   ```

7. 景点与三餐必须按距离衔接，优先减少步行和无意义折返。
8. 默认单段步行阈值为 1.5 公里且 20 分钟；任一指标超过阈值时优先改用公交路线。
9. LLM 只负责整理表达、推荐理由、游玩亮点和天气建议，不负责猜测地点、距离或实时事实。
10. 无论使用小红书还是地图降级链路，都必须查询天气并将天气结合到每日攻略中。
11. 目标城市、游玩天数和出行开始日期都是生成多日攻略的必填字段；缺少任一字段时先追问，不检查登录、不查询工具、不生成攻略。
12. 天气只使用供应商实际返回并能与出行日期精确匹配的预报。超出预报范围时继续生成攻略，但明确标记未覆盖，不使用当前天气冒充未来天气。
13. 天气查询与内容召回解耦：小红书帖子召回和天气并行；地图景点餐饮收集和天气并行；最终生成前汇合。

## 三、当前实现与目标差距

### 1. 请求字段不足

当前 `XhsTripRequest` 只有：

- `destination_city`
- `duration_days`

缺少 `start_date`，因此无法把天气预报稳定映射到具体行程日。

### 2. 路由只有两种

当前路由只有：

- `general_agent`
- `xhs_trip_planner`

多日攻略统一进入小红书链路，没有可确定执行的地图攻略分支。

### 3. 登录卡片不能跳过

当前后端启动小红书登录会话后通过 SSE 发送 `xhs_login_required`，前端只展示等待登录状态。用户不能从卡片切换到地图链路。

### 4. 天气没有进入小红书规划图

高德天气工具和类型已经存在，但当前小红书规划图只收集帖子正文，生成 Prompt 和最终每日结果都没有天气字段。

### 5. 地图工具具备基础能力，但缺少专用编排

现有高德能力已经能够支持：

- 按城市或附近位置搜索 POI。
- 返回 POI ID、地址、类型和 GCJ-02 坐标。
- 对 2 至 20 个位置计算步行或驾车时间矩阵。
- 对最终起终点查询步行、公交、驾车、骑行或电动车路线。
- 查询当前天气与近期预报。

缺少的是确定性的“景点筛选 → 两两分日 → 三餐邻近搜索 → 全链路距离优化 → 结构化攻略”服务。

### 6. 已有缓存不是规划状态

高德客户端已有进程内 TTL 缓存：

- 默认 TTL：300 秒。
- 最大条目数：512。
- 服务重启后丢失。
- 当前天气和天气预报使用不同缓存命名空间。

该缓存可以减少相同参数的重复供应商调用，但不能代替本次 LangGraph 运行状态，也不能作为最终攻略的数据来源。

## 四、实施目标

实施完成后必须满足：

1. “成都三日游”但未给日期时，只追问日期，不启动小红书登录。
2. 字段齐全后仍默认使用小红书。
3. 未登录时，用户可以从登录卡片明确切换到地图与天气方案。
4. 点击跳过会取消当前登录等待，不留下孤立的登录轮询任务。
5. 小红书内容召回与天气查询并行执行。
6. 地图景点餐饮收集与天气查询并行执行。
7. 地图方案每天最多两个景点，顺序固定，地点全部来自高德返回结果。
8. 三餐和景点形成连续路线，默认控制单段步行距离和时间。
9. 每天显示对应自然日和天气覆盖状态。
10. LLM 不能添加未出现在证据包中的景点或餐厅。
11. 最终结果保留供应商、查询时间、天气报告时间、POI ID 和路线依据。
12. 旧普通聊天、单项工具查询、小红书已登录流程和现有 SSE 客户端保持兼容。

## 五、非目标

本次不包含：

- 航班、火车、酒店、预算、库存或预订。
- 新增地图或天气供应商。
- 餐厅评分、实时排队、营业状态、招牌菜真实性验证。
- 景点票价、开放时间、预约政策验证。
- Redis 天气缓存或数据库天气快照表。
- 用户账号级的小红书偏好持久化。
- 复杂的全局旅行商算法或引入新的优化库。
- 重写现有通用 AgentExecutor。
- 在小红书方案中强行套用“每天两个景点”的地图降级模板；小红书方案继续忠实于帖子证据，只新增日期与天气。

## 六、系统不变量

### 1. 日期不变量

- `start_date` 表示第 1 个行程自然日。
- 第 N 天日期为 `start_date + N - 1`。
- 行程结束日期为 `start_date + duration_days - 1`，包含首尾。
- `duration_days` 继续受现有最大天数配置约束。
- 相对日期基于请求上下文中的当前日期、`Asia/Shanghai` 时区和用户明确原文解析。
- 过去日期、冲突日期或无法确定的相对日期必须追问或返回受控校验错误。

### 2. 来源不变量

- 小红书方案中的具体地点继续受选中帖子证据约束。
- 地图方案中的景点和餐厅必须包含有效高德 POI ID 和 GCJ-02 坐标。
- 工具没有返回的地点、距离、天气、温度和路线不得由模型补造。
- LLM 推荐理由属于模型整理建议，不能冒充高德评价、官方介绍或小红书原文事实。

### 3. 天气不变量

- 每次多日攻略运行最多发起一次逻辑天气查询；高德客户端内部可以命中当前缓存。
- 天气按具体日期匹配，不能按列表位置盲目映射。
- 没有匹配预报的日期使用 `unavailable`，字段保持空值并写入原因。
- 天气查询失败不伪造数据；小红书方案可以继续生成并警告，地图方案也可以继续使用已获得的地点和路线事实。
- 最终每天必须有天气覆盖状态，即使状态是不可用。

### 4. 距离不变量

- 距离判断必须来自高德时间矩阵或路线工具。
- 没有计算成功的路段不能写具体距离或耗时。
- 地图方案的地点顺序在进入 LLM 前已经确定；LLM 不得改变顺序而使路线证据失效。
- 地图方案不得为了凑满两个景点使用低质量、跨城市、缺少坐标或重复 POI。

### 5. 协议与取消不变量

- 不删除或改名现有 SSE 事件。
- 新增事件字段使用可选字段，旧前端忽略后仍可运行。
- 用户点击跳过时必须取消旧 SSE 请求，并等待或触发后端现有取消清理路径。
- 取消旧请求后启动地图方案，不复用已取消的 LangGraph 任务。

## 七、请求与内部字段协议

### 1. API 请求扩展

在 `ChatRequest` 增加可选字段：

```python
planning_mode: Literal["xhs", "map_weather"] | None = None
```

语义：

- `None`：保持当前默认行为，路由器判定多日攻略后进入小红书模式。
- `xhs`：显式进入小红书模式。
- `map_weather`：明确跳过小红书登录，直接进入地图降级链路。

服务端不能只依赖前端按钮文本判断降级模式；`planning_mode` 是确定性覆盖字段，用户自然语言仍可作为路由补充。

### 2. 统一规划请求

新增或从现有 XHS 请求模型演进出通用请求：

```python
class CityTripRequest:
    destination_city: str | None
    duration_days: int | None
    start_date: date | None
```

第一版可选偏好仅保留：

```python
interests: list[str]
food_preferences: list[str]
```

可选偏好缺失不阻塞生成。不得在本次顺带引入人数、酒店、预算和交通字段。

### 3. 必填字段检查顺序

固定顺序：

1. 提取城市、天数、开始日期。
2. 使用用户最近一轮明确值覆盖模型提取值。
3. 校验天数、日期和城市。
4. 如果缺少字段，输出一次合并追问并结束本轮。
5. 字段完整后才执行路由覆盖、登录检查或工具查询。

示例追问：

```text
请告诉我计划从哪一天开始游玩，例如“7 月 25 日开始”。
```

## 八、天气证据协议

### 1. 运行态事实模型

建议新增内部结构：

```python
class DailyWeatherEvidence:
    date: date
    coverage: Literal["available", "unavailable"]
    day_weather: str | None
    night_weather: str | None
    day_temperature: str | None
    night_temperature: str | None
    day_wind_direction: str | None
    night_wind_direction: str | None
    day_wind_power: str | None
    night_wind_power: str | None
    unavailable_reason: str | None

class TripWeatherEvidence:
    provider: Literal["amap"]
    city: str
    adcode: str | None
    report_time: str | None
    queried_at: datetime
    days: list[DailyWeatherEvidence]
    warnings: list[str]
```

天气事实模型不包含 LLM 的穿衣或玩法建议。建议字段在最终计划生成阶段单独产生。

### 2. 查询规则

固定调用参数：

```json
{
  "city": "目标城市",
  "forecast": true
}
```

如果地图 POI 已返回可靠 `adcode`，后续同一运行可优先使用 `adcode`；但天气任务与内容任务并行时不等待 POI 返回，直接使用城市名解析即可。

### 3. 日期覆盖规则

对每个行程自然日执行精确日期匹配：

- 全部匹配：所有天 `available`。
- 部分匹配：匹配天正常填充，其余天 `unavailable`，原因是尚未进入供应商预报范围。
- 全部不匹配：所有天 `unavailable`，攻略继续生成并显示统一提醒。
- 调用失败：所有天 `unavailable`，保留安全错误摘要，不向 LLM 或用户暴露内部异常、密钥和 URL。

### 4. 缓存与运行状态

第一版不新增缓存实现：

- 继续使用 `AmapClient` 已有 5 分钟进程内缓存减少重复请求。
- 天气任务完成后把类型化 `TripWeatherEvidence` 放入本次 LangGraph state。
- 最终生成节点直接读取 state，不反向读取缓存。
- 最终攻略保存或渲染天气快照时保留 `queried_at` 和报告时间。
- 未来需要多进程共享时再将 `AmapCache` 接口实现为 Redis，不纳入本次。

## 九、并行执行与汇合设计

### 1. 并行边界

只有在城市、天数和日期完整，且本轮内容模式已经确定后启动天气任务。

小红书模式：

```text
完成登录或确认已经登录
        ↓
并行启动：小红书证据收集 + 天气收集
        ↓
等待两者完成
        ↓
生成小红书攻略
```

地图模式：

```text
确认 map_weather 模式
        ↓
并行启动：地图景点餐饮收集 + 天气收集
        ↓
等待两者完成
        ↓
生成地图攻略
```

### 2. 不在登录等待阶段提前查询天气

用户停留在登录卡片时可能长时间不操作，也可能直接跳过。因此：

- 不在 `wait_xhs_login` 期间启动天气查询。
- 已经登录时，小红书收集和天气立即并行。
- 登录完成后，小红书收集和天气立即并行。
- 点击跳过并启动新地图请求后，地图收集和天气立即并行。

### 3. 任务实现约束

- 可以使用 LangGraph 并行分支，也可以在受控节点内使用 `asyncio.create_task` / `gather`。
- 第一版优先采用明确、易测试的服务层并发，不让模型决定并发。
- 任一任务被取消时必须向子任务传播取消，不遗留天气或地图后台请求。
- 天气失败和内容成功时继续生成；内容失败时不能只用天气生成具体地点攻略。

## 十、登录卡片跳过流程

### 1. SSE 协议

保留 `xhs_login_required`，增加可选字段：

```json
{
  "login_id": "...",
  "expires_at": "...",
  "message": "...",
  "fallback_available": true,
  "fallback_mode": "map_weather"
}
```

旧前端忽略新增字段仍能显示原登录卡片。

### 2. 前端行为

登录卡片增加按钮：

```text
跳过登录，使用地图与天气生成
```

点击后：

1. 按钮进入 loading，防止重复点击。
2. 使用当前 `AbortController` 中止登录等待流。
3. 后端取消路径调用小红书登录取消能力。
4. 在同一对话提交一条可见用户消息：

   ```text
   跳过小红书登录，使用地图与天气继续生成。
   ```

5. 新请求同时传 `planning_mode="map_weather"`。
6. 新请求从最近对话继承城市、天数和日期。
7. 原登录卡片显示“已跳过小红书登录”，新助手消息显示地图规划进度。

### 3. 竞态处理

- 跳过与登录成功同时发生时，以先被服务端接受的最终请求为准；前端只保留一个活动流。
- 新地图流不得等待旧登录取消完成后才查询高德，但旧流必须最终完成取消清理。
- 重复点击不得启动两个地图规划请求。
- 页面刷新后不自动恢复已经取消的登录等待。

## 十一、地图降级收集与优化算法

### 1. 景点候选召回

基础查询：

```json
{
  "city": "目标城市",
  "keywords": "景点",
  "limit": "min(20, max(duration_days * 3, 6))"
}
```

如果用户明确给出兴趣，可增加最多两个并行关键词查询，例如“博物馆”“自然风景”，但总去重候选不得超过 20，避免超过时间矩阵输入上限。

候选过滤：

- 必须有 `poi_id`。
- 必须有 GCJ-02 坐标。
- 城市或行政区信息不得与目标城市明确冲突。
- 按 `poi_id` 去重。
- 排除明显属于餐饮、酒店、购物或非游览目的的结果。
- 保留高德原始搜索顺序和查询来源，不能声称该顺序等于评分或热度。

### 2. 景点距离矩阵与分日

对过滤后的景点候选调用步行时间矩阵：

```json
{
  "locations": "候选景点坐标列表",
  "mode": "walking"
}
```

分日目标数量：

```text
required_attractions = duration_days * 2
```

使用确定性贪心配对，不让 LLM直接配对：

1. 为所有可用景点对计算距离分数。
2. 分数由步行时间、步行距离、供应商搜索顺序和兴趣匹配组成。
3. 优先选择距离近且搜索顺序较高的未使用景点对。
4. 每个景点最多使用一次。
5. 直到形成 `duration_days` 个景点对或候选耗尽。
6. 候选不足时允许部分天只有一个景点，并写入警告；不得加入模型猜测地点凑数。

同一景点对中，搜索顺序较高者默认作为上午景点，另一个作为下午景点。

### 3. 三餐候选搜索

对每个已经确定的景点对：

- 早餐：以上午景点为中心，半径 1500 米，关键词“早餐”，最多 5 条。
- 午餐：以两个景点坐标的本地近似中点为中心，半径 2500 米，关键词“餐厅”或用户饮食偏好，最多 5 条。
- 晚餐：以下午景点为中心，半径 1500 米，关键词“晚餐”或用户饮食偏好，最多 5 条。

中点仅用于附近搜索，不作为展示地点或路线事实。每个餐饮候选仍必须来自高德返回结果。

餐饮过滤：

- 必须有 `poi_id` 和坐标。
- 按 `poi_id` 去重。
- 同一行程默认不重复推荐同一家餐厅。
- 不根据模型猜测营业时间、早餐供应、评分和招牌菜。
- 对结果不足的餐次允许使用更宽泛的“餐饮”关键词重试一次；仍为空则保留餐次占位并提示用户到附近现场选择，不伪造餐厅。

### 4. 每日五点路线优化

每天最多包含：

```text
5 个早餐候选
+ 上午景点
+ 5 个午餐候选
+ 下午景点
+ 5 个晚餐候选
= 17 个位置
```

该数量不超过时间矩阵 20 个位置上限。对这些位置计算步行矩阵并枚举最多 `5 × 5 × 5 = 125` 种餐饮组合，选择以下总路径成本最低的有效组合：

```text
早餐 → 上午景点 → 午餐 → 下午景点 → 晚餐
```

成本包含：

- 四段步行时间之和。
- 四段步行距离之和。
- 超过 1.5 公里或 20 分钟的路段惩罚。
- 重复餐厅惩罚。
- 缺失矩阵结果的组合直接淘汰。

### 5. 最终路线模式

对选中的四个相邻路段逐段判定：

- 距离不超过 1.5 公里且步行时间不超过 20 分钟：使用矩阵中的步行距离与时间。
- 任一指标超出阈值：调用 `amap_plan_route`，模式使用 `transit`，并传目标城市。
- 公交查询失败：保留已知步行距离，路线模式标为未验证，提示用户出发前使用地图导航。

只对最终选中的非步行路段查询公交路线，不对全部候选进行路线调用。

## 十二、地图证据与最终计划结构

### 1. 地图地点证据

建议结构：

```python
class MapPlaceEvidence:
    reference_id: str
    role: Literal["breakfast", "morning_attraction", "lunch", "afternoon_attraction", "dinner"]
    poi_id: str
    name: str
    address: str
    poi_type: str
    location: AmapCoordinate
    search_query: str
    search_rank: int
```

### 2. 路段证据

```python
class RouteLegEvidence:
    origin_ref: str
    destination_ref: str
    mode: Literal["walking", "transit", "unverified"]
    distance_meters: int | None
    duration_seconds: int | None
    route_summary: str | None
```

### 3. 每日地图证据

```python
class MapDayEvidence:
    day_index: int
    date: date
    breakfast: MapPlaceEvidence | None
    morning_attraction: MapPlaceEvidence
    lunch: MapPlaceEvidence | None
    afternoon_attraction: MapPlaceEvidence | None
    dinner: MapPlaceEvidence | None
    route_legs: list[RouteLegEvidence]
```

### 4. 最终每日输出

无论来源模式，最终每天至少包含：

- `day_index`
- `date`
- 天气覆盖状态和天气事实
- 天气相关建议
- 有来源引用的活动或餐饮
- 路线距离与耗时（仅在工具成功时）
- 当日提示和警告

小红书模式继续使用帖子来源引用；地图模式使用高德 POI 与路段引用。不得把高德 POI 伪装为小红书来源。

## 十三、LLM 生成规则

### 1. 小红书模式

输入：

- 用户请求和日期。
- 一至两篇选中小红书正文。
- 每日天气证据。

规则：

- 地点仍只能来自帖子证据。
- 天气可以影响每日提醒和表达，但不能成为添加新地点的理由。
- 天气预报与帖子建议冲突时明确提示，不修改供应商天气事实。
- 每天输出具体日期和天气覆盖状态。

### 2. 地图模式

输入：

- 已确定的每日五点顺序。
- POI 名称、地址、类型和来源引用。
- 路段距离、耗时和模式。
- 每日天气证据。

LLM 可以：

- 润色景点推荐理由。
- 根据景点名称、类型和一般知识介绍大致值得体验的方向。
- 结合天气生成穿衣、雨具、防晒和节奏建议。
- 将结构化证据整理成自然的分日攻略。

LLM 不可以：

- 改变地点顺序。
- 添加未提供的景点、餐厅或路线。
- 声称某地点“评分最高”“必吃榜第一”或正在营业。
- 编造门票、营业时间、具体展品、招牌菜、排队和预约规则。
- 把推荐理由写成高德或官方事实。

### 3. 结构校验

生成后必须验证：

- 天数与请求一致。
- `day_index` 连续。
- 日期连续且与开始日期一致。
- 所有地点引用都在允许来源集合中。
- 地图模式活动顺序与证据一致。
- 路线起终点与相邻地点一致。
- 天气日期与当日日期一致。
- 不存在未引用的具体地点名称。

校验失败时可以进行一次受控修订；仍失败则返回受控错误，不输出未校验攻略。
